# Backend ИЖС Hub

Node.js 22+, Express, PostgreSQL 15+, Sequelize, Socket.IO. Сервер запускает миграции перед открытием порта; повторный и одновременный запуск защищены блокировкой PostgreSQL.

## Локальный запуск

```sh
cd backend
cp .env.example .env
npm ci
npm run dev
```

В `DATABASE_URL` укажите рабочую PostgreSQL. `GET /health` и `/health/ready` проверяют текущую доступность базы, хранилища и фоновых задач; `/health/live` проверяет жизнь процесса. Для отдельного запуска миграций используйте `npm run db:migrate`, для просмотра состояния — `npm run db:migrate:status`.

В контейнере используется Node.js 22. Секреты и локальные загрузки исключены из контекста сборки; каталог `/app/uploads` должен сохраняться в volume. Для production используйте [PRODUCTION.md](PRODUCTION.md): обязательны независимые секреты access/refresh/служебного доступа, HTTPS origin и явное доверие к сети proxy.

## Бизнес-правила

- Регистрация доступна агенту, физлицу и застройщику. Администратор не создаётся через публичную регистрацию. Неподтверждённый застройщик может войти и заполнить профиль, но не управлять объектами или заявками. Отклонение регистрации отзывает его сессии.
- Email сохраняется в нижнем регистре; российские телефоны приводятся к единому формату. Регистрация, профиль и создание застройщика администратором используют одну проверку уникальности, в том числе при одновременных запросах.
- Для свободного объекта можно создать заявки на разных клиентов. Активная заявка закрепляет клиента (телефон, в любом формате записи) на объекте за её автором: повторная заявка того же автора и заявка другого агента на этого клиента возвращают `409`. Закрепление снимается, когда заявка отклонена, отозвана или истекла. Физлицо подаёт заявку на себя, с данными своего профиля, и не может заменить их в заявке.
- ФИО и телефон клиента (`PATCH /applications/:id/client`) автор меняет только пока заявка в статусе `sent`; изменение записывается в `audit_logs` (`entityType=application`).
- Автор отзывает свою заявку через `PATCH /applications/:id/cancel` (`{ "comment"?: string }`) до завершения сделки. Статус `cancelled` финальный, бронь объекта освобождается, застройщик и администраторы получают уведомление. Застройщик и администратор установить `cancelled` не могут.
- Заявка действует семь дней. `PATCH /applications/:id/extend` принимает `{ "days": 1..60 }` и добавляет дни к текущему сроку; автор получает уведомление `application_extended`. Истёкшую заявку нельзя подтвердить, продлить, изменить или отозвать даже до очередного запуска фонового обработчика.
- Порядок статусов: `sent → confirmed → contract_signed → awaiting_payment → commission_available → done`. Разрешено перейти вперёд через несколько этапов. Обратный переход и изменение завершённой/отклонённой/истёкшей/отозванной заявки запрещены. Повтор текущего статуса не создаёт дополнительных уведомлений и истории. `expired` устанавливает сервер, `cancelled` — автор. Если статус меняет администратор, уведомление получает и застройщик.
- Подтверждение резервирует объект только для одной заявки. Отклонение этой заявки освобождает бронь. Завершение продаёт объект и закрывает остальные отправленные заявки. Изменение статуса объекта напрямую не может отменить бронь или продажу, связанную со сделкой; ручная отметка «продан» отклоняет отправленные заявки на объект. Объект с историей заявок нельзя удалить или передать другому застройщику. Объект создаётся и передаётся только подтверждённому застройщику.
- Комиссия рассчитывается сервером при создании заявки: цена × нижняя граница активного тарифа `apartments` / 100, с округлением до копеек. Клиентское `commissionAmount` игнорируется. Без цены или тарифа комиссия остаётся `null`. Изменения цены и тарифа не пересчитывают существующую заявку. В заявке сохраняются `commissionRateId`, `commissionRatePercent` и `commissionBasePrice`. Расчёт использует целые копейки и тысячные доли процента; старые заявки остаются без этих снимков, поскольку историческая ставка неизвестна. Изменения цен и тарифов записываются вместе с автором и значениями до/после в `audit_logs`; администратору доступен `GET /audit` с фильтрами `entityType`, `entityId` и пагинацией.
- Администратор редактирует мероприятие (`PATCH /events/:id`): перенос возможен только до начала и в будущее, вместимость не может стать меньше числа записанных. При переносе напоминания переносятся, а участники получают уведомление `event_updated` (также при смене места или формата). `POST /events/:id/cancel` (`{ "reason"?: string }`) отменяет ещё не начавшееся мероприятие: запись и одобрение закрываются, напоминания снимаются, участники получают `event_cancelled`. Отменённое мероприятие остаётся в списках с `cancelledAt` и `cancelReason`. Участник отменяет свою запись через `DELETE /events/:id/register` до начала мероприятия; место освобождается, администраторы получают уведомление.
- Мероприятие создаётся с датой начала в будущем. Поле `capacity` ограничивает число заявок со статусами `new` и `approved`. Старое название `maxParticipants` поддерживается. Отклонённая регистрация освобождает место, но её последующее одобрение снова проверяет вместимость. После начала мероприятия запись закрыта.
- Уведомления по сделкам и регистрации отправляются в Socket.IO после фиксации корневой транзакции (в том числе созданные через `findOrCreate`). Откат не публикует их пользователям.
- Сообщение в чате заявки создаёт уведомление `application_chat_message`: автору — об ответе администратора, администраторам — о сообщении автора. Пока предыдущее уведомление по этому чату не прочитано, новое не создаётся.
- Профиль: пустой телефон в `PATCH /users/me` означает «не менять», прежний телефон в старом формате принимается без изменений, новый должен быть российским. У агента и застройщика компания обязательна, у физлица всегда пустая. Ошибки валидации возвращаются на русском.
- Списки `/applications/mine`, `/applications/incoming`, `/properties`, `/news`, `/events/registrations` принимают необязательные `page` и `limit` (до 200, только вместе) и тогда возвращают `{ items, total, page, limit }`; без них ответ остаётся массивом. Заявки фильтруются по `status`. `GET /applications/:id` возвращает одну заявку с объектом, историей и автором: автору, застройщику объекта и администратору (остальным `404`). `GET /events` принимает `period=upcoming` (ближайшие первыми) или `period=past` (недавние первыми). `POST /notifications/read-all` отмечает прочитанными все уведомления пользователя.

## Восстановление пароля и удаление аккаунта

`POST /auth/password/forgot` (`{ email }`) всегда отвечает одинаково, существует аккаунт или нет. Существующему пользователю уходит письмо со ссылкой `APP_ORIGIN/reset-password#token=…`: токен передаётся во фрагменте URL и не попадает в журналы серверов. Ссылка действует 60 минут и одноразовая; новый запрос отменяет прежние ссылки. `POST /auth/password/reset` (`{ token, password }`) задаёт пароль, завершает все сеансы и отправляет письмо о смене пароля. В базе хранится только HMAC токена. Ограничения: 20 запросов за 15 минут с адреса, не больше 3 писем в час на один email, 10 попыток сброса за 15 минут. Почта настраивается через `SMTP_URL` и `MAIL_FROM`; в разработке без SMTP письма пишутся в журнал, в production без SMTP восстановление отвечает `503`.

`DELETE /users/me` (`{ password }`) удаляет аккаунт по требованию владельца (152-ФЗ). Персональные данные обезличиваются: email заменяется на `deleted-<id>@deleted.invalid`, удаляются телефон, ФИО, компания, аватар, уведомления, сеансы и ссылки сброса. Имя и email в чатах поддержки и обращениях стираются, будущие записи на мероприятия снимаются, отправленные заявки отзываются с уведомлением застройщика. Данные физлица как клиента стираются из заявок, кроме завершённых сделок (их хранят как сведения о договоре). История сделок остаётся с «Удалённый пользователь». Удаление запрещено, пока есть сделки в работе (от `confirmed` до `commission_available`), застройщику с объектами и единственному администратору. Email освобождается для новой регистрации; удаление фиксируется в `audit_logs` (`entityType=user`).

## Авторизация и документы

API принимает `Authorization: Bearer <access token>`. Access-токен содержит идентификатор действующей серверной сессии. Выход отзывает доступ этой сессии сразу; выход со всех устройств отзывает все сессии; смена пароля сохраняет текущую и закрывает остальные. Refresh-токен хранится в HttpOnly cookie и меняется при обновлении доступа. Вход, регистрация, refresh, выход и обращения в поддержку имеют отдельные ограничения. Неудачные входы ограничены по IP (20 за 15 минут) и по аккаунту (10 за 15 минут, против перебора с разных адресов); успешный вход не тратит лимит, выход доступен и при исчерпании лимита входа. Время ответа на вход не зависит от существования email. Временный отказ базы и проигравший параллельный refresh не стирают cookie успешной сессии.

Для изменяющих запросов к `/auth/refresh`, `/auth/logout` и `/auth/logout-all` передайте значение cookie `csrf_token` в заголовке `x-csrf-token`.

Документы `/uploads/application_docs/*` доступны только автору заявки и администратору. Обычная ссылка в браузере проверяет HttpOnly cookie сессии; API-клиент может передать Bearer. Ответ запрещает кеширование и предлагает скачать файл. Изображения каталога, аватары, новости и обложки мероприятий остаются публичными.

После обновления backend ранее выпущенные access-токены без идентификатора сессии нужно обновить через refresh или войти заново. Адреса API и форматы основных ответов сохранены. Токены в параметрах URL скрываются в журнале запросов. Сообщения поддержки не передают токены в уведомления администратора.

## Миграции и служебные команды

Начальная схема зафиксирована в SQL и не зависит от текущих моделей. Совместимая старая база без `SequelizeMeta` принимается без удаления данных; проверяются столбцы, связи и уникальные индексы. Несовместимая схема останавливает запуск с указанием расхождения. Новые изменения добавляются отдельной миграцией; применённые файлы и снимки схемы не редактируются. Тесты используют те же миграции, что и сервер.

`npm run admin:create` создаёт администратора из `ADMIN_EMAIL` и `ADMIN_PASSWORD` (от 12 символов, до 72 байт UTF-8). Пароль не выводится в журнал; существующий аккаунт не перезаписывается. `src/sync_db.js` оставлен как совместимый вход для запуска миграций, автоматического создания администратора нет.

`npm run seed` требует `ALLOW_SEED=1` и запрещён в production. Сброс через `npm run db:clear` или `SEED_FORCE=1` требует одновременно `NODE_ENV=development` либо `test`, `ALLOW_DB_RESET=1` и `RESET_DATABASE_NAME`, точно совпадающего с именем целевой базы. Сбрасываются схема и реестр миграций, затем схема создаётся заново миграциями.

## Файлы, чаты и фоновые задачи

У загрузок проверяются расширение, MIME и сигнатура содержимого. Для DOCX/XLSX проверяется каталог ZIP и обязательные элементы формата; текстовые файлы принимаются в UTF-8. Замена аватара или обложки, удаление изображения/документа и удаление объекта добавляют очистку старых локальных файлов в `file_deletions` в одной транзакции с изменением данных. Очистка начинается после commit, ошибки диска повторяются с задержкой. Общий файл сохраняется, пока на него ссылается другая запись. Удалённый документ объекта недоступен по старому адресу сразу после удаления записи.

Списки чатов получают последние сообщения непосредственно из базы. Имя клиента и число непрочитанных сообщений сохраняются после ответа администратора. Для списков доступны необязательные `page`/`limit` (до 200); для истории `/support/history` и `/applications/:id/chat/messages` — `limit` (до 200), `beforeId` или `afterId`. Страница истории возвращается в хронологическом порядке; без параметров сохраняется прежний полный ответ.

Socket.IO вынесен в `realtime/`. Сохраняются существующие имена событий. Размер пакета ограничен 64 KiB; по умолчанию — 120 событий на соединение и 2000 на IP за минуту, в пределах одного процесса. При смене аккаунта предыдущие приватные комнаты закрываются. Соединение живёт, пока активна серверная сессия: истечение короткого access-токена его не закрывает, а событие с просроченным токеном той же сессии принимается. Истечение или отзыв сессии закрывает соединение (`auth_expired` / disconnect); отзыв в другом процессе обнаруживается в течение 30 секунд. Неверный токен не даёт новых комнат и не сбрасывает уже выданные. Проверка разрешённого Origin применяется и к WebSocket.

Регистрация на мероприятие сохраняет задачу в `event_reminders`. Доставка уведомления и отметка выполнения фиксируются одной транзакцией. После перезапуска сервер доставляет пропущенные напоминания до начала мероприятия; отклонённые записи и начавшиеся мероприятия не получают их. Существующие регистрации подхватываются автоматически; повторная доставка защищена уникальным ключом. `EVENT_TIME_ZONE` задаёт часовой пояс текста уведомления (по умолчанию `Europe/Moscow`). Истёкшие и отозванные сессии и устаревшие ссылки сброса пароля удаляются через сутки ежечасной задачей. Готовность (`/health/ready`) падает после трёх неудач задачи подряд или при её остановке; одиночная ошибка повторяется на следующем запуске. `RUN_SCHEDULED_JOBS=false` отключает фоновые задачи только в development/test; production требует включённых задач. При завершении процесса сервер дожидается активных HTTP/Socket.IO операций и задач, затем закрывает базу. Очистка файлов откладывается на время согласованной резервной копии.

## Проверки

Тесты работают с настоящей PostgreSQL и сбрасывают данные в тестовой базе. Имя базы обязательно должно заканчиваться на `_test`; рабочую базу использовать нельзя.

Пример отдельной базы для тестов:

```sh
docker run --name ijs-backend-test \
  -e POSTGRES_USER=ijs -e POSTGRES_PASSWORD=ijs_local_test -e POSTGRES_DB=ijshub_test \
  -p 127.0.0.1:55433:5432 -d postgres:15-alpine
```

Если контейнер уже создан, запустите его через `docker start ijs-backend-test`. После готовности PostgreSQL:

```sh
cd backend
npm ci
npm run lint
TEST_DATABASE_URL=postgres://ijs:ijs_local_test@127.0.0.1:55433/ijshub_test npm test
npm audit --omit=dev
```

Покрыты конкурентные заявки и бронирование, истечение сроков, фиксация комиссии, лимиты мероприятий, уникальность аккаунтов, отзыв сессий, права на документы, проверка содержимого и очистка загрузок, поддержка, пагинация, аудит финансовых изменений, доставка после простоя и миграции. Socket.IO проверяется реальными соединениями, включая изоляцию комнат, истечение токенов и отзыв сессий. В CI эти проверки запускаются с PostgreSQL 15 и Node.js 22; отдельный production-прогон проверяет запуск за Caddy, права роли базы, нагрузку, копирование/восстановление и отказ PostgreSQL.

В `package.json` закреплена совместимая CommonJS-версия `uuid` 11.1.1 для Sequelize. Sequelize использует `v1()`/`v4()` без аргументов; совместимость проверяется транзакциями и миграциями. Это закрывает оставшийся дефект зависимости без перехода на устаревшую основную версию Sequelize. Для загрузок используется [Multer 2.4](https://github.com/expressjs/multer/releases/tag/v2.4.0).

## Структура

- `routes/`, `controllers/` — HTTP API и права доступа.
- `validation/` — проверка тела, параметров и фильтров запроса.
- `services/` — бизнес-логика и транзакции.
- `models/` — модели и связи базы.
- `db/migrations/` — последовательные миграции; `db/migrator.js` — их выполнение и учёт.
- `jobs/` — истечение заявок, долговременные напоминания и повторная очистка файлов.
- `middleware/`, `utils/` — сессии, загрузки, ошибки, журналирование.
- `realtime/` — Socket.IO, права на комнаты, ограничения и жизненный цикл сессий.
- `config/`, `ops/` — проверка окружения, готовности и метрики; `backend/ops/` — копирование, восстановление, мониторинг и проверка production-стенда.
- `server.js` — запуск и завершение процесса.
- `tests/` — проверки API на выделенной PostgreSQL.
