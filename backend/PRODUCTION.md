# Production: ИЖС платформа

Поддерживаемая конфигурация: один процесс Node.js 22, PostgreSQL 15 и Caddy с HTTPS. Compose не публикует порты базы и API, а использует отдельную внутреннюю сеть. API работает без root, с файловой системой только для чтения, постоянным volume загрузок, ограничениями памяти и времени запросов. Несколько процессов API требуют общего хранилища лимитов и адаптера Socket.IO; текущая конфигурация допускает только `WEB_CONCURRENCY=1`.

## 1. Подготовка

Нужны Docker Compose с поддержкой `!override`/`!reset`, реальный DNS-домен, доступные порты 80/443 и подключённое независимое хранилище резервных копий. Подготовьте mount, например `/mnt/ijshub-backups`, с владельцем UID/GID 1000 и правами 0700. Для проверки копирования подходит локальный каталог; для восстановления после потери сервера хранилище должно находиться вне этого сервера. Один каталог на том же диске не решает эту задачу.

В корне проекта:

```sh
cd backend
npm ci
npm run ops:configure -- <ваш-домен> /mnt/ijshub-backups
cd ..
docker compose --env-file .env.production -f docker-compose.prod.yml config --quiet
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build --wait
```

`ops:configure` создаёт `.env.production` с правами 0600 и отдельными случайными секретами: JWT, refresh, доступ к метрикам, шифрование копий, администратор PostgreSQL и прикладная роль. Существующий файл никогда не перезаписывается. Файл исключён из Git; не включайте его в образ или артефакты CI. Сохраните ключ шифрования и конфигурацию в отдельном защищённом хранилище: копию без исходного ключа восстановить нельзя.

Production API отклоняет отсутствующие/шаблонные секреты, одинаковые секреты access/refresh/operations, слабые пароли базы, HTTP origin, небезопасные cookie, чрезмерно широкое доверие к proxy и отключённые фоновые задачи. Используйте исходную сеть `BACKEND_SUBNET=172.30.50.0/24`; при конфликте адресов измените её и сохраните явное доверие к ней. `TRUST_PROXY=true` или `1` запрещены. HTTP и Socket.IO одинаково определяют клиентский IP по цепочке доверенных proxy. [Express: доверие к proxy](https://expressjs.com/en/guide/behind-proxies/).

При первичной инициализации создаётся `ijs_app` с `NOSUPERUSER NOCREATEDB NOCREATEROLE`; эта роль владеет прикладной базой и схемой. Пароль администратора и ключ копий не передаются API. API дополнительно проверяет права своей роли при запуске. Инициализирующий скрипт PostgreSQL выполняется только для нового пустого volume.

Для восстановления пароля по email задайте в `.env.production` почтовый ящик отправителя: `SMTP_URL` (`smtps://user:password@smtp.yandex.ru:465` или `smtp://…:587?requireTLS=true`) и `MAIL_FROM` (`ops:configure` подставляет `no-reply@<домен>`). Пароль ящика с особыми символами кодируйте в URL. В production разрешены только соединения с TLS; ссылки и пароли SMTP не попадают в журнал. Пока `SMTP_URL` пуст, `POST /api/auth/password/forgot` отвечает `503`, остальное API работает. Ошибки отправки записываются в журнал как `mail_send_failed`. Для доставки настройте у домена SPF и DKIM вашего почтового провайдера.

Администратора приложения создайте через `npm run admin:create` внутри API, передав `ADMIN_EMAIL` и `ADMIN_PASSWORD` через защищённый файл окружения или интерактивный ввод. Пароль от 12 символов, до 72 байт; существующая запись не перезаписывается. После безопасного задания переменных в текущей сессии выполните:

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml \
  run --rm --no-deps -e ADMIN_EMAIL -e ADMIN_PASSWORD api node src/create-admin.js
unset ADMIN_EMAIL ADMIN_PASSWORD
```

В аргументах команды передаются только имена переменных. Не используйте demo-сиды в production.

Проверки после запуска:

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml ps
curl --fail https://<ваш-домен>/api/health/ready
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail 30 api backup monitor
```

## 2. Существующая база и обновления

Перед обновлением сохраните зашифрованную копию базы вместе с файлами и проверьте восстановление в отдельную базу. Первым обновлением выполняется переход к явным миграциям: совместимая старая схема принимается без удаления данных, несовместимая останавливает запуск. Выполните прогон на копии реальной базы, а затем сверку количества аккаунтов, объектов, заявок, истории статусов и финансовых значений. Автоматическая проверка в CI использует тестовые данные и не заменяет проверку конкретной рабочей базы.

Для старого PostgreSQL volume вручную подготовьте роль без административных прав и передайте ей владение прикладными таблицами, последовательностями и enum-типами. Новый init-скрипт не меняет уже созданный volume. Не используйте `db:clear`, `sync({alter:true})` или `sync({force:true})` для обновлений. Начальная схема и применённые миграции неизменяемы; добавляйте новый файл миграции.

Существующий volume загрузок должен быть доступен UID/GID 1000 на чтение и запись. Перед первым запуском API без root проверьте владельца и права сохранённых файлов и каталогов; исправляйте их с сохранением содержимого.

Рекомендуемый порядок: проверенная копия → восстановление на отдельном стенде → миграции → бизнес-сценарии → обновление одного API. Миграции блокируются PostgreSQL advisory lock; резервная копия ждёт завершения изменения схемы. Для отката сначала остановите API и восстановите согласованную копию базы и файлов в новые места. Не запускайте старый код против схемы, несовместимой с ним.

## 3. Резервные копии

Сервис `backup` делает копию при старте и раз в сутки, повторяет ошибку через пять минут. В архив включаются PostgreSQL и только файлы, на которые ссылаются записи снимка: аватары, изображения, документы объектов, обложки и вложения заявок. База экспортируется через `pg_dump --snapshot` из той же транзакции, что читает ссылки на файлы. На время снимка удаления файлов откладываются в очереди; запись новых данных продолжает работать. [PostgreSQL: согласованные снимки pg_dump](https://www.postgresql.org/docs/15/app-pgdump.html).

Архив шифруется AES-256-GCM со случайным IV. Копия публикуется атомарно, зеркалируется в `BACKUP_MIRROR_PATH`, сверяется по SHA-256, затем сохраняется успешный статус. Файлы копий имеют права 0600; `BACKUP_KEEP=14` задаёт число последних копий, минимум 2. Нешифрованные промежуточные файлы находятся в приватном рабочем volume с правами 0700 и удаляются при завершении операции; API этот volume не видит. Свободного места должно хватать на базу и вложения (при восстановлении — также на извлечённый архив). После аварийного отключения проверьте оставшиеся временные каталоги. Для защиты диска целиком используйте шифрование хранилища сервера.

Внеплановая копия:

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm --no-deps backup ops/backup.js
```

Заявленный интервал — 24 часа, следовательно потенциальная потеря данных после аварии — до 24 часов. Если это неприемлемо, сократите интервал и рассмотрите отдельный режим PostgreSQL PITR/WAL. Время восстановления зависит от объёма данных; измеряйте его на реальной копии, а не по размеру тестового стенда.

## 4. Восстановление

Восстанавливайте только доверенный архив в **новую пустую базу** и **пустой volume загрузок**. Утилита требует `ALLOW_DB_RESTORE=1` и точное совпадение `RESTORE_DATABASE_NAME`. Заполненная база или каталог отклоняются. Проверяются GCM-подпись, безопасные пути архива, отсутствие ссылок/специальных файлов и SHA-256 базы/вложений. `pg_restore` выполняется одной транзакцией. [PostgreSQL: pg_restore](https://www.postgresql.org/docs/15/app-pgrestore.html).

Создайте, например, `ijshub_restore` с владельцем `ijs_app` через администратора PostgreSQL. Подготовьте приватный `.env.restore` с правами 0600:

```dotenv
RESTORE_DATABASE_NAME=ijshub_restore
RESTORE_DATABASE_URL=postgres://ijs_app:<действующий-пароль>@db:5432/ijshub_restore
RESTORE_BACKUP_FILE=<имя-выбранного-архива>.tar.gz.enc
```

Ключ `BACKUP_ENCRYPTION_KEY` в `.env.production` должен совпадать с ключом создания выбранной копии. Восстановление:

```sh
docker compose --env-file .env.production --env-file .env.restore \
  -f docker-compose.prod.yml -f docker-compose.restore.yml \
  run --rm --no-deps restore
```

Данные появятся в новой базе и отдельном volume `restored_uploads`. Не переключайте рабочий API автоматически: сначала запустите миграции и проверьте восстановленную копию на отдельном стенде. После проверки остановите API и задайте новую `DATABASE_URL` и новое хранилище загрузок одним согласованным изменением Compose. При ошибке сохраняется `.restore-in-progress`; API отказывается запускаться с таким хранилищем. Не удаляйте маркер без проверки завершения восстановления. Повторный прогон выполняйте в новое пустое место.

## 5. Готовность, наблюдение и уведомления

- `/health/live` — жизнь процесса, без обращения к базе.
- `/health/ready` и совместимый `/health` — доступность PostgreSQL, права на хранилище, отсутствие незавершённого восстановления и успешные/своевременные фоновые задачи; при отказе `503`, во время завершения тоже `503`. Проверка базы использует отдельное короткое соединение, поэтому не зависает за исчерпанным пулом.
- `/metrics` — Prometheus: число и суммарная длительность HTTP-запросов, активные запросы, память процесса, время работы и состояние задач. Это суммарные метрики; процентиль задержки измеряется нагрузочным тестом.
- `/ops/status` — состояния задач и очередей удаления/напоминаний.

Служебные маршруты требуют отдельный `Authorization: Bearer <OPS_TOKEN>`; Caddy и nginx закрывают их с публичной стороны. Сбор метрик настраивается из внутренней сети. Токены и пароли скрываются в структурированных журналах. Ротация журналов контейнеров ограничена 5 файлами по 10 MiB.

`monitor` проверяет готовность, очереди и состояние копий каждые 30 секунд. После трёх подряд неудачных проверок сообщает `production_alert`, при восстановлении — `production_recovered`. Причины: недоступность API/служебной проверки, напоминания с опозданием более пяти минут, удаления старше часа, копия старше 26 часов, ошибка копирования либо отсутствие зеркала. Укажите `MONITOR_WEBHOOK_URL` для доставки JSON-событий в вашу систему оповещения; при отказе доставки монитор повторяет её. Без webhook события доступны только в журнале `monitor` — перед публичным запуском настройте внешний сбор журнала или webhook и проверьте получение тестового события. Сам monitoring-контейнер должен контролироваться внешней системой.

API ограничивает время PostgreSQL-запроса (15 секунд), ожидания соединения (5 секунд) и завершения процесса (25 секунд). После SIGTERM новые бизнес-запросы отклоняются, активные HTTP/Socket.IO операции и задачи завершаются, затем закрывается пул. Не применяйте `kill -9` для штатного обновления.

## 6. Проверка перед релизом

```sh
cd backend
npm ci
npm run lint
TEST_DATABASE_URL=postgres://<роль>:<пароль>@localhost:5432/ijshub_test npm test
npm audit --omit=dev
npm run ops:rehearse
```

`ops:rehearse` создаёт уникальный Compose-проект с приватным окружением, не использует рабочую базу, не публикует порты и не отправляет внешних сообщений. Проверяет реальную production-конфигурацию API/Caddy/backup/monitor: права PostgreSQL, HTTPS cookie, WebSocket через Caddy, приватность служебных маршрутов, 1000 объектов, 100 заявок и 5000 сообщений, нагрузку через Caddy, зашифрованную копию и её зеркало, неверный ключ, полное восстановление, обновление наполненной старой схемы, потерю/возврат PostgreSQL, оповещение в журнале и штатное завершение. После проверки удаляет только свой проект и volumes. `--skip-build` повторно использует ранее собранные `ijs-check-*:local`.

Нагрузочный профиль: 200 запросов, 10 одновременно, каталог/свои заявки/чаты/мероприятия, отсутствие ошибок и p95 ≤ 1000 ms. Это воспроизводимая проверка на тестовых данных; для целевого сервера проверяйте профиль, объём базы и число пользователей вашего проекта. Отдельный `npm run ops:load-test` требует `LOAD_TEST_URL`, допускает `LOAD_TEST_TOKEN` для приватных сценариев. Внешняя цель требует явного `ALLOW_LOAD_TEST=1`; без него разрешён только локальный API.

В CI выполняются тесты на Node.js 22/PostgreSQL 15, линтер, аудит production-зависимостей и полный изолированный production-прогон. Реальный DNS/TLS, независимый mount, получение внешних оповещений и обновление копии конкретной рабочей базы проверяются на инфраструктуре развёртывания.
